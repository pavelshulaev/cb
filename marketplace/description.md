## Текст для карточки

Модуль для интеграции 1С-Битрикс с «Клиентской базой» через её REST API:
двусторонний обмен данными, таблицами и пользователями без ручной выгрузки.

Часть линейки интеграционных модулей для 1С-Битрикс от rover-it.me — среди
опубликованных решений также amoCRM, MailChimp и другие CRM- и
сервис-интеграции.

### Что делает модуль

Покрывает основные разделы API «Клиентской базы»: таблицы, строки и данные
таблиц, пользователей. Обращение к любому методу API — через единообразный
набор классов в пространстве имён `Rover\CB\Rest`, без прямой работы с HTTP
и авторизацией:

```php
use Bitrix\Main\Loader;
use Rover\CB\Rest\User;

if (Loader::includeModule('rover.cb')) {
    $users = User::getInstance()->getList();
}
```

Авторизация, повторное использование сессии и разбор ответов API — на
стороне модуля. Методы классов соответствуют методам API 1:1, включая
фильтрацию по точному соответствию полей.

Модуль реализует версию API «Клиентской базы» v1.0. Для большинства сценариев
интеграции — выгрузки и синхронизации данных, таблиц, пользователей — этого
достаточно.

### Когда нужен не модуль, а разработчик

Готовый набор классов закрывает базовый обмен данными. Он не решает
нестандартные задачи: сложный маппинг полей, синхронизацию с третьей
системой, бизнес-логику на события изменения данных, миграцию из другого
решения. Это уже не задача модуля из коробки, а задача индивидуальной
разработки на 1С-Битрикс.

Если у вашего проекта именно такой случай — [опишите задачу](https://rover-it.me/support/new/?module=rover.cb).

### Требования

- PHP 8.1 или выше (проверена совместимость с PHP 8.2);
- «Главный модуль» версии 24.0.0 или выше;
- mod_rewrite на сервере.

## Заметки по правке

- **Числа, которые не проверял и не стал придумывать**: количество установок,
  число релизов. Для такого модуля они, скорее, работают против позиционирования
  («мало кто скачал» читается хуже, чем отсутствие цифры) — сознательно не
  включал.
- **Ссылку на GitHub (`github.com/pavelshulaev/cb`) из старого текста убрал.**
  Не проверял, актуален ли репозиторий относительно текущего кода модуля
  (в этой сессии менялись `lib/rest.php`, `lib/helper/log.php` и другие файлы).
  Публиковать неактуальный код рядом с текстом про профессионализм — риск
  обратного эффекта. Если репозиторий поддерживается и синхронизирован —
  можно вернуть отдельной строкой в конце раздела «Что делает модуль».
- **Требование «Конструктор административной части» (rover.fadmin) 1.6.9+»
  из старого текста убрано** — текущий `Dependence::checkBase()` такой
  зависимости не проверяет и модуль её не использует (в отличие от
  rover.mailchimp, где `rover.fadmin` реально подключается в `options.php`).
  Требование «модуль PHP CURL» тоже убрано: текущая проверка зависимостей
  его не требует, а `HttpClient` ядра Bitrix не обязан использовать curl.
- Версии в требованиях синхронизированы с фактическим `Dependence`
  ([lib/service/dependence.php](../lib/service/dependence.php)) после
  недавнего фикса `checkMainVer()` — до фикса проверка версии «Главного
  модуля» не работала, но заявлять в карточке требование, которое код не
  проверяет, было бы нечестно и раньше.
- Ссылка на форму обращения — `https://rover-it.me/support/new/?module=rover.cb`
  без `type`/`title`: в коде модулей эти параметры собираются динамически
  на PHP и урлэнкодятся, для статичного текста карточки взял только
  проверенный по коду базовый путь и модуль, без выдуманных параметров.
- Пример кода сокращён до минимума (без дампа результата, как было в старом
  тексте) — карточка не документация, а витрина; подробности — в README
  модуля после установки.
- Дисклеймер про версию API v1.0 сформулирован как факт, а не извинение —
  в духе «строго и профессионально»: не «к сожалению, старая версия», а
  «этого достаточно для большинства сценариев», с явным пределом ниже.
